# Коммит и pull request

1. Проверь текущую ветку, `git status --short`, обычный и staged diff. Определи объём по исходной задаче и поручению. Если в одном файле смешаны правки разных задач и граница неясна, уточни, какие фрагменты включить. Сохрани чужие изменения и индекс вне согласованного объёма.
2. Перед коммитом выполни правило ретро из AGENTS.md. Сверь результаты проверок с коммитом. Повтори проверки, если после них изменился проверяемый код. Выдели неисполненные проверки и известные блокеры.
3. Предложи в чате точный русский заголовок от результата правки. Для нескольких коммитов покажи все заголовки по порядку. Дождись явного «да» на эти заголовки перед созданием коммитов или переписыванием их сообщений. При изменении заголовка снова покажи новый вариант.
4. Добавь конкретные согласованные пути и проверь итоговый staged diff. При посторонних staged-файлах используй коммит только по выбранным путям, если они целиком относятся к задаче. В теле сообщения по-русски укажи причину и проверки, если они полезны читателю. Для многострочного сообщения используй временный файл и `git commit -F <файл>`.
5. После коммита покажи SHA, сообщение и оставшиеся рабочие изменения, если они есть.

## Отправка в GitHub

- «Сделай коммит» запускает подготовку к подтверждению заголовка. «Отправь ветку на GitHub» разрешает push. «Открой PR» разрешает отправить нужную рабочую ветку и открыть PR. Сверь целевой репозиторий, ветку и базу, сохрани согласованный объём. При первой отправке рабочей ветки установи upstream. Для PR сначала проверь разницу с базой и наличие открытого PR для этой ветки.
- Используй авторизованный GitHub-инструмент или `gh`. Для `gh pr create` передай явные `--repo`, `--base`, `--head`, `--title` и `--body-file`. Напиши заголовок и описание по-русски. Укажи, что изменилось для пользователя или проекта, какие проверки реально прошли и какие остались открыты. Верни ссылку на PR или точную причину, по которой публикация остановилась.
