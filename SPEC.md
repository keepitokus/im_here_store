# «Я здесь». Спецификация продукта и harness для разработки

Версия 0.1. Описывает продукт и локальный harness для Codex. Harness поддерживает осмотр, подготовку спецификации и реализацию с отдельным ревью.

## 1. Зачем нужен продукт

«Я здесь» помогает собрать разрозненные фотографии и личные истории в цифровую книгу, которую можно подарить близкому человеку.

### Сценарии и критерии приёмки

Действующие правила собраны по пути автора в [разделе 6](#6-действующие-правила-продукта).

- [Выбор издания и стоимость](#выбор-издания-и-стоимость)
- [Черновик и предпросмотр](#черновик-и-предпросмотр)
- [Фотографии, голос и видео](#фотографии-голос-и-видео)
- [Публикация и управление книгой](#публикация-и-управление-книгой)
- [Чтение по приватной ссылке](#чтение-по-приватной-ссылке)
- [Проба книги на GitHub Pages](#проба-книги-на-github-pages)

Для текущего MVP сверяй README, код и тесты по затронутому сценарию. Серверный `DEMO_MODE` с симулятором платежей и статический GitHub Pages — отдельные среды проверки.

### Целевые сценарии исходного ТЗ

- Демокнига каждого издания включает текст, фото, голосовое сообщение и видеокружочек.
- Для медиа предусмотрены загрузка готового аудио и видео, запись с микрофона и камеры, воспроизведение и обработка отказа в разрешениях. Запись проверяют в Safari на iOS и Chrome на Android. Ориентиры ТЗ — 15–30 фотографий, до 15 МБ на фото или аудиофайл, до 10 голосовых по 3 минуты и до 5 видеокружочков по 60 секунд.
- Для читателя предусмотрены раскрытие хронологии по событиям на телефоне, две колонки на компьютере и воспроизведение одной медиавставки за раз.
- Для тяжёлых файлов в статическом редакторе предусмотрено хранение в IndexedDB.

### Решения, которые стоит подтвердить при изменении соответствующего сценария

| Тема | Исходное ТЗ | Текущий README или код |
| --- | --- | --- |
| Продление | Ручное продление на 12 месяцев за 990 ₽. ТЗ формулирует правило для книги в целом. | Продление доступно только для `first-year`, на 365 дней за 990 ₽. |
| Уведомления | Email за 14 и 3 дня до окончания срока. | README описывает уведомления за 30, 7 и 1 день и 90-дневный льготный период для `first-year`. |
| Архив | ZIP с текстом в TXT/HTML и папками фото, аудио и видео. | `src/app/api/books/[bookId]/export/route.ts` отдаёт JSON-файл. |
| Первый экран | «Когда слова важнее подарка». | README называет слоганом «Истории, к которым возвращаются». Эта формулировка также есть в `src/app/page.tsx`. |
| Число фотографий | Рекомендовано 15–30, верхний предел указан диапазоном 30–35. | README описывает предел в 30. |

Исходное ТЗ — внешний файл `ТэЗэшечка.md` в каталоге `ImHere`. Этой выжимки достаточно для навигации по репозиторию. Когда новая задача касается спорного требования, владелица проекта выбирает целевое поведение, после чего решение попадает в спеку и критерии проверки.

## 2. Что такое harness

Harness — локальная обвязка, которая принимает задачу разработчицы, подбирает настройки запуска Codex и собирает результат. `AGENTS.md` объясняет Codex, как работать в репозитории. Маршрутизатор подбирает модель **до запуска**. Codex читает нужные файлы, выполняет задачу и проверяет результат. MCP даёт доступ к отдельному инструменту или внешнему сервису.

Работа над изменением проходит через этапы `arch → coder → reviewer`. В первой версии эти шаги укладываются в один запуск с коротким планом, правкой, проверкой diff и тестами. Для критичных правок можно явно запустить отдельное ревью с доступом только на чтение. [Инструкции AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md) · [Запуск из скрипта](https://learn.chatgpt.com/docs/non-interactive-mode).

### Вход и результат

- На входе — описание задачи и, по возможности, ожидаемый результат, режим (`pages`, `server` или оба) и связанные файлы. Режим запуска `inspect` означает чтение, `apply` разрешает правку в рабочей копии. По умолчанию используется `inspect`.
- `-DryRun` показывает выбранный профиль, модель, глубину рассуждения и причину выбора. Проверка работает локально без вызова модели и без изменений репозитория.
- Ручной выбор профиля доступен для сравнения результатов. В `apply` критический профиль задаёт минимальную планку для задач по оплате, приватному доступу или данным. Ручной выбор модели и профиля подчиняется ограничениям рабочей среды.
- Итог запуска содержит выбранный профиль и модель, изменённые файлы, результаты проверок, статус и доступные метрики времени и токенов. Отсутствующие метрики помечаются как недоступные. Журнал хранит сводку без исходного запроса, секретов, пользовательского контента и сырого потока событий.

### Что отложено

- Добавить отдельный CI для GitHub PR. Начать с ESLint, проверки типов и Vitest, затем подключить стабильный мобильный сценарий конструктора. Текущий workflow Pages обслуживает публикацию.
- Устранить три исходных ошибки `react-hooks/set-state-in-effect` в браузерных редакторе и кабинете. При исправлении проверить вход, открытие черновика по ссылке из кабинета и повторное открытие в Pages.
- Перед большой переделкой конструктора попросить архитектора подготовить карту «редактор → хранение → предпросмотр». На карте указать общие части и границы серверного режима и GitHub Pages. Использовать её, чтобы перепроектировать мобильный интерфейс, сохранить черновики и проверить согласованность отображения книги.

### Как выбирается модель

Профиль — имя в конфигурации harness, которое связывает задачу, модель и глубину рассуждения. Стартовые соответствия ниже следует сверить с доступностью моделей в локальном CLI перед первым реальным запуском. [Выбор модели](https://learn.chatgpt.com/docs/model-selection).

| Профиль | Основание для выбора | Стартовая модель / глубина |
| --- | --- | --- |
| Критичный | Платежи, публикация, авторизация, PIN и доступ к медиа, миграции, удаление или перенос данных, изменение архитектуры нескольких подсистем | `gpt-6.2-astra` / `high` |
| Визуальный | Главный результат оценивается по скриншотам или в браузере. Например, вёрстка мобильной хронологии или визуальный регресс витрины | `gpt-6.1-terra` / `medium` |
| Стандартный | Фича, рефакторинг, баг или тесты с несколькими связанными изменениями. Сюда же попадают задачи с неясным объёмом | `gpt-6.2-sol` / `medium` |
| Лёгкий | Ясная локальная правка документации или копирайта, поиск файла, небольшой обратимый фикс с известным местом | `gpt-6.2-sol` / `low` |

Порядок проверки признаков: критичный, визуальный, лёгкий, затем стандартный. Для первого прототипа признаки задаются небольшим списком правил по тексту и указанным путям. Объяснение решения указывает, какое правило сработало. При неясной границе задачи сначала уместен запуск `inspect`. Если осмотр выявил критичный путь, следующий запуск выбирает критичный профиль. Если заданная модель недоступна, запуск сообщает об этом и предлагает доступное соответствие профиля, которое можно явно выбрать. Если процесс уже менял файлы, перед повторным запуском проверь его diff.

### Первый исполняемый прототип

1. **Классификация.** Из корня репозитория запусти `.\scripts\Get-CodexRoute.ps1 -Task 'Исправить опечатку в README'`. Скрипт выводит профиль, модель, глубину рассуждения и причину. Для задачи с известным файлом передай относительный путь через `-Path`. Правила проверяются по порядку из [scripts/codex-routes.json](scripts/codex-routes.json). Для сухого запуска достаточно PowerShell.
2. **Вызов Codex.** Запусти `.\scripts\Invoke-CodexTask.ps1 -Task 'Найди команду тестов в package.json' -Path 'package.json'`. Скрипт передаёт задачу через stdin, запускает Codex из корня репозитория с `read-only` и возвращает ответ, время и доступный счётчик токенов. Для предварительного просмотра выбора модели добавь `-DryRun`. Для реального прогона нужен установленный Codex CLI с авторизацией. Для спецификации и реализации используй команды из раздела 5.
3. **Проверка результата.** `status: completed` сообщает о завершении хода Codex. Чтобы понять, прочитал ли он нужный файл и выполнил ли проверки, смотри `result`. Сравни состояние Git до и после осмотра. Для проверки всей цепочки начни с небольшой явно разрешённой правки и просмотри её diff. Каждый этап выполняется один раз.
4. **Уточнение правил.** Сравнить маршруты на реальных задачах, отметить ошибочные решения и поправить признаки. При добавлении нового профиля сначала определить задачу, где существующие настройки дают заметно худший результат.

| Пробная задача | Ожидаемый выбор |
| --- | --- |
| Исправить опечатку в README | Лёгкий |
| Обновить мобильную хронологию по скриншоту | Визуальный |
| Исправить порядок событий после повторного открытия черновика | Стандартный |
| Исправить двойное продление при повторе платёжного вебхука, включая состояние экрана оплаты | Критичный |

Первая версия готова, когда сухой запуск правильно разбирает все четыре примера, осмотр оставляет рабочую копию без изменений, разрешённая правка проходит выбранные проверки, а ошибочный запуск возвращает понятный статус без автоматической публикации. Автоматический выбор действует для задач, отправленных через скрипт. В обычной сессии Codex модель выбирается средствами клиента.

## 3. Инструменты и MCP

| Инструмент | Когда использовать |
| --- | --- |
| `rg` и Git | Базовый набор уже доступен. `rg --files` помогает найти файл, `rg -n` — точный фрагмент. Сужай поиск по каталогу и читай совпадения порциями. Для этого MCP не требуется. |
| GitHub | Подключать, когда понадобятся issues, PR и логи Actions. Для Codex доступен коннектор GitHub. Для CLI можно выбрать `gh` или официальный GitHub MCP. Для просмотра хватит доступа на чтение к нужному репозиторию. [GitHub MCP](https://github.com/github/github-mcp-server) |
| Serena | Опробовать, когда регулярно нужен поиск определений и ссылок TypeScript через языковой сервер. Сравнить обычный поиск и Serena на одинаковых задачах: время, входные токены, число вызовов и точность найденных мест. [Документация Serena](https://oraios.github.io/serena/) |
| Браузерные проверки | Для регрессов редактора и читателя использовать существующие сценарии в `tests/*.spec.ts`. Браузерный MCP имеет смысл, если регулярно нужны интерактивные проверки и доступные средства их не покрывают. |

Начальный маршрут работает с локальным репозиторием и CLI. Подключения добавляются по одному, когда появляется конкретный сценарий и понятен его объём доступа.

## 4. Роли и проектные навыки

Роль определяет, кто выполняет этап. Навык подсказывает, как работать с конкретной частью «Я здесь». В конфигурации ролей модель не закреплена. Корневой запуск через harness выбирает модель по таблице профилей, а роли используют настройки, которые им передаёт родительская сессия. Запуск отдельных ролей можно явно запросить в обычной сессии Codex. [Роли Codex](https://learn.chatgpt.com/docs/agent-configuration/subagents)

## 5. Разработка по спецификации

Спецификация задачи описывает, **что должно происходить и как это проверить**. План объясняет, **как добиться этого в коде**. [Раздел 6](#6-действующие-правила-продукта) задаёт действующие правила, а спецификация задачи уточняет конкретное изменение.

1. **Архитектор** фиксирует сценарий, область изменений и наблюдаемые критерии приёмки. Сверяет их с текущим кодом и затем предлагает план и проверки. Если нужно выбрать между разными правилами продукта, решение принимает владелица проекта до реализации.
2. **Кодер** получает спецификацию и план, меняет код и проверяет критерии. Если в коде обнаружится ограничение, меняющее ожидаемое поведение, сначала обнови спецификацию и согласуй этот выбор. Уточнения реализации, сохраняющие критерии приёмки, можно внести в план по ходу работы.
3. **Ревьюер** получает ту же спецификацию, diff и результаты проверок. Сверяет каждый существенный критерий с поведением приложения и отмечает непроверенные сценарии.

Для локальной правки с ясным результатом достаточно пары строк в задаче. Для изменения нескольких подсистем или правил оплаты, публикации, доступа и хранения заполни шаблон до правок. Для задачи на одну сессию его можно оставить в чате. Если по задаче работать в нескольких сессиях, сохрани спецификацию и план в одном Markdown-файле под `docs/specs/`.

```markdown
## Спецификация задачи
- Цель и сценарий пользователя
- Ожидаемое поведение и затронутые режимы — сервер, Pages или оба
- Границы правки и открытые продуктовые решения
- Критерии приёмки, включая ближайший пограничный случай

## План
1. Шаг — границы изменения, затронутые модули и зависимости от других шагов
   - Ожидаемый результат — наблюдаемое поведение и связанные критерии приёмки
   - Проверка — способ воспроизведения, ожидаемый исход и затронутые режимы
```

Для локальной правки достаточно одного шага. Крупную задачу дели на шаги с самостоятельным проверяемым результатом. Укажи зависимость, если следующий шаг опирается на результат предыдущего. Для шага, меняющего пользовательский путь, запиши основной браузерный сценарий и ближайший значимый пограничный случай. Для сервера и Pages, когда затронуты оба режима, укажи отдельные прогоны.

В задаче с хронологией шаги могут выглядеть так.

1. **Сохранение порядка в редакторе.** Ожидаемый результат — после повторного открытия виден сохранённый порядок. Проверка — на мобильном размере переставить три синтетических события, сохранить и снова открыть черновик. Пограничный случай — черновик с одним событием открывается и сохраняется без изменений.
2. **Порядок в предпросмотре.** Шаг опирается на сохранение порядка в редакторе. Ожидаемый результат — предпросмотр показывает тот же порядок, что и повторно открытый черновик. Проверка — открыть предпросмотр после перестановки и отдельно для черновика с одним событием. Если затронуты сервер и Pages, пройти оба шага в каждом режиме.

В отчёте о браузерной проверке укажи фактически пройденный сценарий, режим и наблюдаемый результат. Если прогон недоступен, укажи конкретную причину и отметь сценарий как непроверенный. Ревьюер сверяет это с согласованным планом.

### Запуск через harness

Из корня репозитория запусти архитектора в режиме чтения. Готовый документ сохранится в `docs/specs/chronology.md`. Если файл уже существует, выбери другое имя или отредактируй его.

```powershell
$task = 'Сохранять порядок событий после повторного открытия черновика'
$paths = @('src/components/editor-wizard.tsx', 'src/components/free-editor.tsx')
.\scripts\Invoke-CodexTask.ps1 -Mode Plan -Task $task -Path $paths -SpecFile 'chronology.md'
```

Проверь или поправь документ перед реализацией. Запуск `Apply` подтверждает содержимое файла и разрешает правки в рабочей копии.

```powershell
$report = .\scripts\Invoke-CodexTask.ps1 -Mode Apply -Task $task -Path $paths -SpecFile 'chronology.md'
$report.coder.result
$report.reviewer.result
$report.reviewFollowUp.summary.chat
```

Harness делает отдельные вызовы Codex для ролей. Кодер работает с `workspace-write`. После завершения кодера ревьюер читает diff и критерии с `read-only`. Статус `reviewed` означает, что ревью завершилось и может содержать замечания. При блокере или ошибке этапа цепочка останавливается. Если кодер успел изменить файлы, просмотри `git diff` и новые файлы перед повторным запуском.

Для обоих режимов можно добавить `-DryRun`, чтобы увидеть этапы, модель и глубину рассуждения. Для `Apply` поле `conditionalStages` показывает возможные этапы между первым ревью и локальной записью правила. Для Plan и Apply профиль определяется по исходной задаче и путям затронутых файлов. При запуске Apply перечисли фактические пути из согласованного плана, включая критичные подсистемы. Спецификация целиком передаётся исполнителям; примеры, исторический контекст и отчёт архитектора внутри неё не участвуют в классификации. Изменения самого harness по умолчанию проверяются в текущем чате локально. В режиме по умолчанию `Inspect` достаточно одной задачи.

`-DryRun` показывает в `skills` навыки для вложенных этапов, выбранные по задаче и путям. Поле `chatSkills` показывает условия применения навыков в основном чате. Правила находятся в [scripts/codex-skill-routes.json](scripts/codex-skill-routes.json). Каждый вложенный этап, включая исправления и повторное ревью, получает инструкции прочитать выбранные навыки. В отчёте этапа поле `skills` показывает, что было передано исполнителю.

### Быстрые автопроверки Apply

В плане перечисли конкретные файлы Vitest относительно корня. Можно указать новый тест, который появится на этапе кодера. Для браузерных и других проверок используй обычный текст плана.

```apply-checks/v1
{"tests":["tests/editor-copy.test.ts","tests/timeline-view.test.ts"]}
```

Перед кодером `Apply` фиксирует исходное состояние и запускает доступные проверки для сравнения. После кодера обвязка сама запускает ESLint по JS/TS-файлам, появившимся или изменившимся за этот запуск, и Vitest по явным путям из плана. План без блока по-прежнему работает. В таком запуске Vitest остаётся проверкой кодера по критериям задачи. `-DryRun` показывает выбор без запуска проверок.

Отчёт `checks.first` передаётся первому ревьюеру, а `checks.afterRepair` содержит свежий прогон перед повторным ревью. Для каждого инструмента видны файлы, код выхода и краткая диагностика. Статусы показывают успешный прогон, пропуск, подтверждённую исходную ошибку, сбой или недоступность проверки. Совпавшая исходная диагностика отмечается как `pre_existing`. Для остальных сбоев принадлежность к правке подтверждает ревьюер. Подтверждённые дефекты идут в обычный пакет исправлений. Неразрешённый сбой или недоступная выбранная проверка даёт `blocked`. Для записи продуктового правила выбранные тесты должны пройти.

### Один пакет исправлений после ревью

Первый ревьюер за один проход проверяет весь актуальный diff, новые файлы и все существенные критерии. В отчёте всегда видны три заголовка — 🔴 **Критические ошибки и блокеры**, 🟡 **Стоит исправить**, 🟢 **Необязательные мелочи**. В пустой группе напиши «Нет замечаний». Красный уровень означает серьёзные последствия или блокировку обязательного сценария. Жёлтый означает конкретный дефект или значимый недостаток. Зелёный означает необязательную рекомендацию.

Приложи один блок `apply-review-followup/v2` с массивом `findings`. Каждый пункт содержит уникальный `id` из букв, цифр, дефиса или подчёркивания, уровень `severity` (`red`, `yellow`, `green`), наблюдаемый эффект `description` и дальнейшее действие `action`. Пустой список записывается как `{"findings":[]}`. Сохраняй ID при повторной проверке.

| Действие | Дополнительные обязательные поля |
| --- | --- |
| `repair` | Путь от корня репозитория `path`, строка или точное место `location`, ID критерия или точная формулировка из спеки `reference`, конкретная правка `fix` и способ её проверить `check`. |
| `owner` | Вопрос владелице в `question`. |
| `dependent` | В `reason` укажи, от какого ответа зависит исправление. |
| `needs_evidence` | В `reason` укажи, какой проверки или какого уточнения не хватает. |
| `recommendation` | Предложение в `suggestion`. Это действие для всех зелёных пунктов. |

Для красного и жёлтого уровней выбери действие по возможности исправления. Все независимые `repair` в рамках спеки идут кодеру одним пакетом вместе с исходной спецификацией. Вопрос владелице и зависящие от него правки остаются открытыми. Перед возвратом harness сверяет рабочие файлы, индекс Git, `SPEC.md` и утверждённую спецификацию. Если пакет пуст, достаточно первого ревью.

После единственного возврата новый процесс ревьюера с `read-only` получает оба отчёта кодера и первый отчёт ревьюера. Проверь весь актуальный diff, новые файлы и все существенные критерии, затем добавь один блок той же версии.

```apply-review-followup/v2
{
  "outcomes": [
    {"id":"R1","status":"fixed","evidence":"После сохранения и повторного открытия второе событие осталось первым."}
  ],
  "newFindings": []
}
```

В `outcomes` укажи каждый первоначальный ID ровно один раз. Значения `fixed`, `open`, `owner`, `recommendation`, `not_rechecked` означают «исправлено», «открыто», «требует решения владелицы», «рекомендация», «повторно не проверено». В `evidence` опиши основание, вопрос или причину пропуска проверки. В `newFindings` перечисли новые пункты по первоначальной схеме со свежими ID. На этом цепочка завершается при любом результате.

Основная сессия выводит в чат `$report.reviewFollowUp.summary.chat` с первоначальными группами, итогом каждого ID и новыми замечаниями. Те же данные доступны в массивах `initialFindings`, `outcomes` и `newFindings` внутри `summary`. Если повторный этап пропущен, завершился ошибкой или дал невалидный отчёт, итог показывает доступный статус и причину. Для ошибок разбора исходного блока используй сохранённый `firstReviewer.result` и `reason`. Неизвестная версия, лишний блок (включая v1 вместе с v2), повтор ID, ошибка полей или ссылка вне спеки останавливают возврат.

#### Совместимость с прежними отчётами

Для прежних отчётов действует контракт `apply-review-followup/v1`. Решение `repair` подходит, когда есть ровно одно существенное замечание, исправление следует из утверждённой спецификации и результат можно проверить.

```apply-review-followup/v1
{
  "decision": "repair",
  "finding": "При повторном открытии черновика меняется порядок событий.",
  "path": "src/components/editor-wizard.tsx",
  "location": "Восстановление списка событий при открытии черновика",
  "reference": "C1",
  "observed": "После сохранения второе событие снова отображается первым.",
  "check": "Переставить два события, сохранить черновик и открыть его снова. Сверить порядок."
}
```

Укажи путь от корня репозитория и строку или конкретное место в коде. В `reference` скопируй ID критерия или точный фрагмент утверждённого пункта. Harness проверяет поля и наличие ссылки в спецификации. Ревьюер отвечает за соответствие замечания этому пункту и за конкретность исправления.

| Решение | Поля и дальнейшее действие |
| --- | --- |
| `clean` | Только `{"decision":"clean"}`. Существенные критерии проверены. Необязательные предложения можно явно отметить в обычном отчёте. |
| `repair` | Все поля из примера обязательны. Перед возвратом кодеру harness сверяет с первым ревью файлы рабочей копии, индекс Git, `SPEC.md` и утверждённую спецификацию. При изменении или ошибке сверки владелица получает причину остановки. |
| `owner` | Укажи `decision`, `kind` и текст причины в `reason`. Для продуктового выбора (`product_choice`) и неоднозначного замечания (`unclear`) добавь вопрос в `question`. Для нескольких существенных замечаний используй `multiple`, для прочих причин, включая недостающую проверку, — `other`. |

Обычный текстовый отчёт без блока завершает первое ревью по прежним правилам. Ошибка формата, повтор блока или конфликт структурированных результатов останавливает автоматическое исправление. Кодер получает исходную спецификацию и одно проверенное замечание. После исправления отдельный ревьюер с `read-only` проверяет текущий diff, новые файлы, результаты обоих вызовов кодера и все существенные критерии. На этом лимит исчерпан. Если итоговое решение отличается от `clean` или отсутствует, владелица получает отчёт с причиной остановки.

В `$report.reviewFollowUp` доступны первые отчёты `firstCoder` и `firstReviewer`, решение `firstDecision` и причина завершения `reason`. После повтора там же появляются `repairCoder`, `finalReviewer` и `finalDecision` по мере готовности. Поля `$report.coder` и `$report.reviewer` содержат последние завершённые отчёты каждой роли. При сбое повторного этапа статус запуска — `blocked`, а `errorStage` указывает `repairCoder` или `finalReviewer`. Рабочие правки доступны для разбора.

### Как утвердить и записать изменение правила

Если меняется правило продукта, архитектор находит его в разделе 6. При расхождении ТЗ и MVP владелица выбирает формулировку до запуска `Apply`. Архитектор описывает каждый существенный критерий и способ его проверки под уникальным ID. Для общего поведения сервера и Pages указывает проверку каждого режима. Для оплаты, доступа и хранения включает применимые гарантии, ошибки и повтор операции.

В спецификацию задачи входит один блок следующего формата. Значения в примере заменяются текстом задачи.

```product-rule-update/v1
{
  "section": "### Черновик и предпросмотр",
  "before": "Точная текущая строка правила.",
  "after": "Утверждённая новая строка правила.",
  "requiredCriteria": ["C1"]
}
```

`section` содержит полный заголовок темы. `before` и `after` содержат одну или несколько полных строк внутри неё. Переводы между строками в JSON записываются как `\n`. Последний перевод строки остаётся за пределами фрагмента. Идентификатор состоит из букв, цифр, дефиса или подчёркивания. Значения `unknown` и `optional` зарезервированы для замечаний. Блок с ошибкой останавливает `Apply` до кодера. Согласие на дословную запись даёт запуск с этой спецификацией.

Кодер реализует и проверяет поведение. Раздел 6 записывает локальный шаг после ревью. Ревьюер сохраняет обычный отчёт с маркером `REVIEWED` и добавляет один блок.

```product-rule-review/v1
{
  "criteria": [
    {"id": "C1", "status": "passed", "evidence": "Название выполненной проверки и наблюдаемый результат на этой реализации."}
  ],
  "findings": [],
  "missingCriteria": []
}
```

Каждому утверждённому ID соответствует один результат `passed`, `failed` или `unverified` с основанием. Для `passed` укажи выполненную проверку или проверяемое наблюдение из плана. В `findings` внеси **каждое** открытое замечание из отчёта объектом с текстом `description` и полем `impact`. Влияние обозначается ID затронутого критерия, `unknown` для неопределённого влияния или `optional` для явно необязательного пункта. В `missingCriteria` перечисли пропущенные существенные критерии словами.

В задаче с записью правила каждый пункт v2 дополнительно содержит `impact`. У каждого открытого красного и жёлтого пункта пара `impact` и `description` дословно совпадает с соответствующей парой в `product-rule-review/v1`, включая число повторов. Зелёному пункту соответствует `optional`. Для `repair` в `reference` и `impact` требуется один и тот же обязательный ID со статусом `failed`. Каждый `failed` объясняется явным существенным замечанием по этому ID. Для возврата нужны основания по всем обязательным ID и пустой `missingCriteria`. Противоречие отчётов или `unverified` останавливает возврат. Для прежнего `repair` v1 по-прежнему требуется единственное существенное замечание с точным совпадением ID и описания.

После возврата запись разрешает только валидный финал по каждому первоначальному ID и всем обязательным критериям с основаниями. У всех критериев должен быть результат `passed`. Оставшийся или новый красный либо жёлтый пункт, неопределённое влияние и пропуск существенной проверки блокируют запись. Явно необязательная рекомендация допустима. Для запуска без повтора те же ворота записи применяются к первому ревью. Перед записью harness сверяет рабочую копию и индекс со снимком, сделанным непосредственно перед подтверждающим ревью.

После завершённого ревью читай `$report.productRuleUpdate` вместе с отчётами кодера и ревьюера. Локальный шаг проверяет основания, состав ID, замечания и сохранность рассмотренных файлов. Он заменяет единственный совпавший фрагмент под блокировкой файла. Индекс Git сохраняется.

| Статус обновления | Что произошло |
| --- | --- |
| `not_requested` | В утверждённой спецификации отсутствует блок изменения правила. Достаточно обычного текстового ревью. |
| `updated` | Все существенные критерии подтверждены. Утверждённая формулировка записана. |
| `already_current` | В теме уже есть ровно одна новая формулировка, а прежняя отсутствует. Повтор сохранил файл и время изменения. |
| `blocked` | Результаты ревью неполны, есть существенное замечание или обнаружен конфликт. Поле `reason` указывает причину. |
| `error` | Ошибка чтения, блокировки или записи. После ошибки записи шаг восстанавливает исходные байты. Если восстановление тоже сорвалось, `reason` содержит путь к резервной копии. |

При `blocked` или `error` устрани указанную причину и повтори `Apply` с той же согласованной спецификацией. Верхнеуровневый `reviewed` означает завершение ревью при любом из этих результатов.

## 6. Действующие правила продукта

Открытые вопросы о продлении, уведомлениях, формате архива, слогане и пределе фотографий собраны в [разделе 1](#решения-которые-стоит-подтвердить-при-изменении-соответствующего-сценария).

### Выбор издания и стоимость

Главный экран знакомит с изданием «Наша история». Витрина напоминает тёплый бумажный магазин и независимый журнал. Для четырёх изданий доступны демо-книги. Демо открывается без входа.

| Издание | Идентификатор | Публикация |
| --- | --- | --- |
| «Наша история» | `love-story` | 4 990 ₽ |
| «Мама, спасибо» | `mother-thanks` | 5 990 ₽ |
| «Твой день» | `your-day` | 5 990 ₽ |
| «Мой первый год» | `first-year` | 4 990 ₽ |

### Черновик и предпросмотр

Автор бесплатно собирает обложку, ответы на тематические вопросы, хронологию и финальное письмо. События можно переставлять. Примеры видны в пустых полях и отсутствуют в сохранённой книге. До оплаты автор может посмотреть книгу глазами получателя на телефоне и компьютере.

### Фотографии, голос и видео

Автор может добавлять фотографии в черновик. Сервер принимает JPEG, PNG и WebP.

### Публикация и управление книгой

Автор входит в кабинет и сохраняет черновики и медиа на сервере. Подтверждённый разовый платёж публикует книгу на 12 месяцев и открывает приватную ссылку и QR-код. Повторное подтверждение того же платежа безопасно. Автосписания запрещены.

Автор может отредактировать опубликованную книгу по прежней ссылке, изменить PIN и скачать архив.

### Чтение по приватной ссылке

Адресат открывает книгу на телефоне или компьютере без регистрации.

Приватный просмотр использует случайный токен, запрет индексации и проверку PIN, если он задан. Медиа подчиняются доступу к книге.

### Проба книги на GitHub Pages

Витрина и редактор загружаются из статического экспорта. Черновик сохраняется в браузере. При попытке оплатить автор видит демонстрационное сообщение и может перейти к локальному предпросмотру.
