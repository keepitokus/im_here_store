# «Я здесь». Спецификация продукта и harness для разработки

Версия 0.1. Описывает продукт и локальный harness для Codex. Harness поддерживает осмотр, подготовку спецификации и реализацию с отдельным ревью.

## 1. Зачем нужен продукт

«Я здесь» помогает собрать разрозненные фотографии и личные истории в цифровую книгу, которую можно подарить по ссылке или QR-коду. Автор начинает бесплатно, видит, что получит адресат, и платит за публикацию. Адресат открывает книгу на телефоне или компьютере без регистрации. Главный экран знакомит с изданием «Наша история» и слоганом «Когда слова важнее подарка». Интерфейс напоминает тёплый бумажный магазин и независимый журнал.

| Издание | Идентификатор | Публикация |
| --- | --- | --- |
| «Наша история» | `love-story` | 4 990 ₽ |
| «Мама, спасибо» | `mother-thanks` | 5 990 ₽ |
| «Твой день» | `your-day` | 5 990 ₽ |
| «Мой первый год» | `first-year` | 4 990 ₽ |

### Сценарии и критерии приёмки

| Сценарий | Ожидаемое поведение по продуктовому ТЗ |
| --- | --- |
| Витрина | Все четыре издания доступны. У каждого своя демо-книга с текстом, фото, голосовым сообщением и видеокружочком. Демо открывается без входа. |
| Черновик | Автор заполняет обложку, тематические вопросы, хронологию и финальное письмо. События можно переставлять. Примеры видны в пустых полях и отсутствуют в сохранённой книге. Предпросмотр даёт оценить мобильную и настольную вёрстку. |
| Медиа | Редактор принимает фото и готовые аудио/видео и поддерживает запись с микрофона и камеры. ТЗ рекомендует 15–30 фото, до 15 МБ на фото или аудиофайл, до 10 голосовых по 3 минуты и до 5 видеокружочков по 60 секунд. Проверяются загрузка, воспроизведение и обработка отказа в доступе к камере или микрофону. Для записи отдельно проверяются Safari на iOS и Chrome на Android. |
| Чтение | На мобильном хронология раскрывается по событиям, на десктопе используется двухколоночная сетка. Одновременно играет одна медиавставка. Приватный просмотр использует случайный токен, запрет индексации и проверку PIN, если он задан. Медиа подчиняются доступу к книге. |
| GitHub Pages | Витрина и редактор загружаются из статического экспорта. Структура черновика хранится в браузере, тяжёлые файлы — в IndexedDB. Оплата заменена демонстрационным сообщением с переходом к локальному предпросмотру. |
| Production | Автор входит в кабинет и сохраняет черновики и медиа на сервере. Подтверждённый разовый платёж публикует книгу на 12 месяцев и открывает ссылку и QR. Повторное подтверждение того же платежа безопасно. Автор может отредактировать опубликованную книгу по прежней ссылке, изменить PIN и скачать архив. Автосписания запрещены. |

Строки таблицы описывают целевое поведение. Для текущего MVP сверяй README, код и тесты по затронутому сценарию. Серверный `DEMO_MODE` с симулятором платежей и статический GitHub Pages — отдельные среды проверки.

### Решения, которые стоит подтвердить при изменении соответствующего сценария

| Тема | Исходное ТЗ | Текущий README или код |
| --- | --- | --- |
| Продление | Ручное продление на 12 месяцев за 990 ₽. ТЗ формулирует правило для книги в целом. | Продление доступно только для `first-year`, на 365 дней за 990 ₽. |
| Уведомления | Email за 14 и 3 дня до окончания срока. | README описывает уведомления за 30, 7 и 1 день и 90-дневный льготный период для `first-year`. |
| Архив | ZIP с текстом в TXT/HTML и папками фото, аудио и видео. | `src/app/api/books/[bookId]/export/route.ts` отдаёт JSON-файл. |
| Первый экран | «Когда слова важнее подарка». | README называет слоганом «Истории, к которым возвращаются». Эта формулировка также есть в `src/app/page.tsx`. |
| Число фотографий | Рекомендовано 15–30, верхний предел указан диапазоном 30–35. | README описывает предел в 30. |

Исходное ТЗ — внешний файл `ТэЗэшечка.md` в каталоге `ImHere`. Этой выжимки достаточно для навигации по репозиторию. Когда новая задача касается спорного требования, владелица проекта выбирает целевое поведение, после чего решение попадает в спеку и критерии проверки.

## 2. Что такое harness

Harness — локальная обвязка, которая принимает задачу разработчицы, подбирает настройки запуска Codex и собирает результат. `AGENTS.md` объясняет Codex, как работать в репозитории. Маршрутизатор подбирает модель **до запуска**. Codex читает нужные файлы, выполняет задачу и проверяет результат. MCP даёт доступ к отдельному инструменту или внешнему сервису.

Работа над изменением проходит через этапы `arch → coder → reviewer`. В первой версии эти шаги укладываются в один запуск с коротким планом, правкой, проверкой diff и тестами. Для критичных правок можно явно запустить отдельное ревью с доступом только на чтение. [Инструкции AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md) · [Запуск из скрипта](https://learn.chatgpt.com/docs/non-interactive-mode).

### Вход и результат

- На входе — описание задачи и, по возможности, ожидаемый результат, режим (`pages`, `server` или оба) и связанные файлы. Режим запуска `inspect` означает чтение, `apply` разрешает правку в рабочей копии. По умолчанию используется `inspect`.
- `-DryRun` показывает выбранный профиль, модель, глубину рассуждения и причину выбора. Проверка работает локально без вызова модели и без изменений репозитория.
- Ручной выбор профиля доступен для сравнения результатов. В `apply` критический профиль задаёт минимальную планку для задач по оплате, приватному доступу или данным. Ручной выбор модели и профиля подчиняется ограничениям рабочей среды.
- Итог запуска содержит выбранный профиль и модель, изменённые файлы, результаты проверок, статус и доступные метрики времени и токенов. Отсутствующие метрики помечаются как недоступные. Журнал хранит сводку без исходного запроса, секретов, пользовательского контента и сырого потока событий.

### Как выбирается модель

Профиль — имя в конфигурации harness, которое связывает задачу, модель и глубину рассуждения. Стартовые соответствия ниже следует сверить с доступностью моделей в локальном CLI перед первым реальным запуском. [Выбор модели](https://learn.chatgpt.com/docs/model-selection).

| Профиль | Основание для выбора | Стартовая модель / глубина |
| --- | --- | --- |
| Критичный | Платежи, публикация, авторизация, PIN и доступ к медиа, миграции, удаление или перенос данных, изменение архитектуры нескольких подсистем | `gpt-6.2-astra` / `high` |
| Визуальный | Главный результат оценивается по скриншотам или в браузере. Например, вёрстка мобильной хронологии или визуальный регресс витрины | `gpt-6.1-terra` / `medium` |
| Стандартный | Фича, рефакторинг, баг или тесты с несколькими связанными изменениями. Сюда же попадают задачи с неясным объёмом | `gpt-6.2-sol` / `medium` |
| Лёгкий | Ясная локальная правка документации или копирайта, поиск файла, небольшой обратимый фикс с известным местом | `gpt-6.2-sol` / `low` |

Порядок проверки признаков: критичный, визуальный, лёгкий, затем стандартный. Для первого прототипа признаки задаются небольшим списком правил по тексту и указанным путям. Объяснение решения указывает, какое правило сработало. При неясной границе задачи сначала уместен запуск `inspect`. Если осмотр выявил критичный путь, следующий запуск выбирает критичный профиль. Если заданная модель недоступна, запуск сообщает об этом и предлагает доступное соответствие профиля, которое можно явно выбрать. Если процесс уже менял файлы, перед повторным запуском проверь его diff.

### Первый исполняемый прототип

1. **Классификация.** Из корня репозитория запусти `.\scripts\Get-CodexRoute.ps1 -Task 'Исправить опечатку в README'`. Скрипт выводит профиль, модель, глубину рассуждения и причину. Для задачи с известным файлом передай относительный путь через `-Path`. Правила проверяются по порядку из [scripts/codex-routes.json](scripts/codex-routes.json). Для сухого запуска достаточно PowerShell.
2. **Вызов Codex.** Запусти `.\scripts\Invoke-CodexTask.ps1 -Task 'Найди команду тестов в package.json' -Path 'package.json'`. Скрипт передаёт задачу через stdin, запускает Codex из корня репозитория с `read-only` и возвращает ответ, время и доступный счётчик токенов. Для предварительного просмотра выбора модели добавь `-DryRun`. Для реального прогона нужен установленный Codex CLI с авторизацией. Для спецификации и реализации используй команды из раздела 5.
3. **Проверка результата.** `status: completed` сообщает о завершении хода Codex. Чтобы понять, прочитал ли он нужный файл и выполнил ли проверки, смотри `result`. Сравни состояние Git до и после осмотра. Для проверки всей цепочки начни с небольшой явно разрешённой правки и просмотри её diff. Каждый этап выполняется один раз.
4. **Уточнение правил.** Сравнить маршруты на реальных задачах, отметить ошибочные решения и поправить признаки. При добавлении нового профиля сначала определить задачу, где существующие настройки дают заметно худший результат.

| Пробная задача | Ожидаемый выбор |
| --- | --- |
| Исправить опечатку в README | Лёгкий |
| Обновить мобильную хронологию по скриншоту | Визуальный |
| Исправить порядок событий после повторного открытия черновика | Стандартный |
| Исправить двойное продление при повторе платёжного вебхука, включая состояние экрана оплаты | Критичный |

Первая версия готова, когда сухой запуск правильно разбирает все четыре примера, осмотр оставляет рабочую копию без изменений, разрешённая правка проходит выбранные проверки, а ошибочный запуск возвращает понятный статус без автоматической публикации. Автоматический выбор действует для задач, отправленных через скрипт. В обычной сессии Codex модель выбирается средствами клиента.

## 3. Инструменты и MCP

| Инструмент | Когда использовать |
| --- | --- |
| `rg` и Git | Базовый набор уже доступен. `rg --files` помогает найти файл, `rg -n` — точный фрагмент. Сужай поиск по каталогу и читай совпадения порциями. Для этого MCP не требуется. |
| GitHub | Подключать, когда понадобятся issues, PR и логи Actions. Для Codex доступен коннектор GitHub. Для CLI можно выбрать `gh` или официальный GitHub MCP. Для просмотра хватит доступа на чтение к нужному репозиторию. [GitHub MCP](https://github.com/github/github-mcp-server) |
| Serena | Опробовать, когда регулярно нужен поиск определений и ссылок TypeScript через языковой сервер. Сравнить обычный поиск и Serena на одинаковых задачах: время, входные токены, число вызовов и точность найденных мест. [Документация Serena](https://oraios.github.io/serena/) |
| Браузерные проверки | Для регрессов редактора и читателя использовать существующие сценарии в `tests/*.spec.ts`. Браузерный MCP имеет смысл, если регулярно нужны интерактивные проверки и доступные средства их не покрывают. |

Начальный маршрут работает с локальным репозиторием и CLI. Подключения добавляются по одному, когда появляется конкретный сценарий и понятен его объём доступа.

## 4. Роли и проектные навыки

Роль определяет, кто выполняет этап. Навык подсказывает, как работать с конкретной частью «Я здесь». В конфигурации ролей модель не закреплена. Корневой запуск через harness выбирает модель по таблице профилей, а роли используют настройки, которые им передаёт родительская сессия. Запуск отдельных ролей можно явно запросить в обычной сессии Codex. [Роли Codex](https://learn.chatgpt.com/docs/agent-configuration/subagents)

| Роль | Когда вызвать | Что получить |
| --- | --- | --- |
| [`architect`](.codex/agents/architect.toml) | Перед изменением нескольких подсистем или при расхождении ТЗ и MVP | План, критерии приёмки и затронутые сценарии |
| [`coder`](.codex/agents/coder.toml) | Когда ожидаемое поведение согласовано | Правку и результаты проверок |
| [`reviewer`](.codex/agents/reviewer.toml) | Когда есть diff и нужна независимая проверка | Замечания с файлами, условиями проявления и последствиями |

| Навык | Область |
| --- | --- |
| [`$ya-zdes-book-editor`](.agents/skills/ya-zdes-book-editor/SKILL.md) | Издания, подсказки, черновики, хронология, медиа и предпросмотр |
| [`$ya-zdes-pages-export`](.agents/skills/ya-zdes-pages-export/SKILL.md) | Статический экспорт, префикс Pages, кабинет и браузерное сохранение |
| [`$ya-zdes-book-lifecycle`](.agents/skills/ya-zdes-book-lifecycle/SKILL.md) | Оплата, публикация, продление, доступ к книге и архив |

Запрос «Запусти `architect` с `$ya-zdes-book-editor` и предложи план исправления порядка событий после открытия черновика» запускает этап проектирования. После согласования можно поручить правку `coder`, а затем передать diff `reviewer`. Для небольшой правки вызови нужный навык напрямую. Навыки также могут подбираться по описанию задачи. [Навыки Codex](https://learn.chatgpt.com/docs/agent-configuration/skills)

## 5. Разработка по спецификации

Спецификация задачи описывает, **что должно происходить и как это проверить**. План объясняет, **как добиться этого в коде**. Спецификация продукта в начале этого файла задаёт общие правила, а спецификация задачи уточняет конкретное изменение.

1. **Архитектор** фиксирует сценарий, область изменений и наблюдаемые критерии приёмки. Сверяет их с текущим кодом и затем предлагает план и проверки. Если нужно выбрать между разными правилами продукта, решение принимает владелица проекта до реализации.
2. **Кодер** получает спецификацию и план, меняет код и проверяет критерии. Если в коде обнаружится ограничение, меняющее ожидаемое поведение, сначала обнови спецификацию и согласуй этот выбор. Уточнения реализации, сохраняющие критерии приёмки, можно внести в план по ходу работы.
3. **Ревьюер** получает ту же спецификацию, diff и результаты проверок. Сверяет каждый существенный критерий с поведением приложения и отмечает непроверенные сценарии.

Для локальной правки с ясным результатом достаточно пары строк в задаче. Для изменения нескольких подсистем или правил оплаты, публикации, доступа и хранения заполни шаблон до правок. Для задачи на одну сессию его можно оставить в чате. Если по задаче работать в нескольких сессиях, сохрани спецификацию и план в одном Markdown-файле под `docs/specs/`.

```markdown
## Спецификация задачи
- Цель и сценарий пользователя
- Ожидаемое поведение и затронутые режимы — сервер, Pages или оба
- Границы правки и открытые продуктовые решения
- Критерии приёмки, включая ближайший пограничный случай

## План
- Порядок изменений и затронутые модули
- Как проверить каждый критерий и где потребуется ручная проверка
```

Для задачи с хронологией критерий может звучать так. Автор меняет порядок трёх событий, сохраняет черновик и открывает его заново. Редактор и предпросмотр показывают сохранённый порядок. Если правка затрагивает оба режима, этот сценарий проверяется отдельно на сервере и в Pages.

### Запуск через harness

Из корня репозитория запусти архитектора в режиме чтения. Готовый документ сохранится в `docs/specs/chronology.md`. Если файл уже существует, выбери другое имя или отредактируй его.

```powershell
$task = 'Сохранять порядок событий после повторного открытия черновика'
$paths = @('src/components/editor-wizard.tsx', 'src/components/free-editor.tsx')
.\scripts\Invoke-CodexTask.ps1 -Mode Plan -Task $task -Path $paths -SpecFile 'chronology.md'
```

Проверь или поправь документ перед реализацией. Запуск `Apply` подтверждает содержимое файла и разрешает правки в рабочей копии.

```powershell
$report = .\scripts\Invoke-CodexTask.ps1 -Mode Apply -Task $task -Path $paths -SpecFile 'chronology.md'
$report.coder.result
$report.reviewer.result
```

Harness делает отдельные вызовы Codex для ролей. Кодер работает с `workspace-write`. После завершения кодера ревьюер читает diff и критерии с `read-only`. Статус `reviewed` означает, что ревью завершилось и может содержать замечания. При блокере или ошибке этапа цепочка останавливается. Если кодер успел изменить файлы, просмотри `git diff` и новые файлы перед повторным запуском.

Для обоих режимов можно добавить `-DryRun`, чтобы увидеть этапы, модель и глубину рассуждения. В `Apply` в выборе модели учитывается также утверждённая спецификация. В режиме по умолчанию `Inspect` по-прежнему достаточно одной задачи.
