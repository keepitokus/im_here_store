## Проект

- Если идея функции пришла из другого проекта, опиши её через сценарий пользователя «Я здесь» и критерии приёмки. В поручениях для harness, спецификациях, коде, комментариях и истории изменений опускай название проекта-источника, ссылки на него и пути к его файлам.

- «Я здесь» — русскоязычный конструктор цифровых книг-воспоминаний. Путь автора: выбрать издание, бесплатно собрать черновик, посмотреть книгу глазами получателя, оплатить публикацию и подарить приватную ссылку или QR-код.
- Держи мобильный сценарий первым. Сохраняй спокойную журнальную подачу без искусственного дефицита, фальшивых скидок и отзывов. Используй вопросы и примеры выбранного издания. Пустое поле с плейсхолдером остаётся пустым в данных и в книге.
- Продуктовые требования, расхождения с MVP и порядок выбора модели описаны в [SPEC.md](SPEC.md). Если задача затрагивает спорное правило, уточни целевое поведение до изменения.

## Как работать

Используй в чате навык `ya-zdes-clarify-product` по просьбе владелицы и по своей инициативе, когда по разговору видно, что продуктовый выбор мешает двигаться дальше. Если трудно выбрать между вариантами или понять, с чего начать, сразу задай один конкретный вопрос. После разбора переходи к `Plan` по просьбе владелицы. Для задач с уже определённым результатом следуй обычному процессу ниже.

Если после выполнения запроса уместен следующий шаг, предложи одно конкретное действие коротким вопросом в конце ответа. Ответ «да» означает согласие на предложенное действие.

1. Проверь `git status --short` и определи затронутый режим. Найди файл через `rg --files` или совпадение через `rg -n`, по возможности ограничив поиск нужным каталогом. Сначала прочитай несколько строк вокруг совпадения (`rg -n -C 2`). Расширяй чтение, когда остаётся конкретный вопрос, например кто вызывает функцию или какой тест проверяет её поведение. Сохраняй чужие правки.
2. Для Next.js сверяйся с локальной документацией по инструкции выше. Для простой задачи зафиксируй ожидаемый результат и переходи к точечной правке. Для изменений цен, публикации, авторизации, приватного доступа, хранения или нескольких подсистем сначала подготовь спецификацию задачи и план по [SPEC.md](SPEC.md#5-разработка-по-спецификации).
3. Применяй существующие компоненты и доменную логику. Проверь обычный путь пользователя и ближайший пограничный случай. При работе с UI проверь мобильное состояние в браузере, если доступен.
4. Просмотри diff и сообщи, что изменилось, какие проверки прошли и что осталось непроверенным. Публикация, push, merge и деплой выполняются по явному поручению.

Для бага или браузерной проверки сам выбирай инструмент по задаче. Используй Chrome DevTools MCP для интерактивного воспроизведения, консоли, запросов и производительности. Используй Playwright для повторяемых шагов и проверки результата. Если MCP недоступен, продолжай проверку через Playwright, когда это возможно. Для обоих инструментов используй локальный сервер и синтетические данные.

## Карта репозитория

- `src/app/` — страницы Next.js App Router и серверные обработчики в `api/`. `src/components/` — витрина, редактор, кабинет и читатель.
- `src/lib/catalog.ts` — издания и цены. `src/lib/editor-copy.ts` — подсказки. `src/lib/books.ts`, `commerce.ts`, `media.ts` — серверная логика книг, платежей и медиа. `src/lib/browser-demo.ts` — браузерное хранение.
- GitHub Pages использует `GITHUB_PAGES=1`, префикс `/im_here_store` и отдельный экспорт в `out/`. Серверный `DEMO_MODE` нужен для локальной симуляции. Статические страницы должны работать без серверного API.
- Храни цены в копейках. Сохраняй разовую оплату, идемпотентность обработки платежей и контроль доступа к приватным книгам и медиа. Используй синтетические данные для проверок и примеров.

## Команды

Команды запускаются из корня. Установка по lockfile — `npm ci`. Локальный сервер — `npm run dev` на порту `43123`. Линтер — `npm run lint`. Vitest — `npm test`, выборочно — `npm test -- tests/<имя>.test.ts`. Серверная сборка — `npm run build`.

Для проверки GitHub Pages используй `bash scripts/export-github-pages.sh` в отдельной рабочей копии или CI. Скрипт временно перемещает и подменяет маршруты в `src/app/`. Проверяй ссылки и ассеты с префиксом Pages.

## Выбор модели и инструменты

В этом репозитории принимай поручения обычным текстом в чате. Запуск PowerShell и выбор параметров harness выполняй сам через `scripts/Invoke-CodexTask.ps1`. Создавай отдельный процесс только для работы над проектом, когда нужен осмотр кода, спецификация или реализация. На вопросы о предыдущем ответе и уже известных фактах отвечай прямо.

- Для выбора проектных навыков используй [таблицу маршрутов](scripts/codex-skill-routes.json). В основном чате применяй правила `chatTrigger`, а при работе напрямую прочитай подходящие навыки по задаче и путям. Если при работе выяснилось, что затронута ещё одна подсистема, прочитай её навык и включи обнаруженные пути при следующем запуске этапа.
- Пиши сообщения коммитов, заголовки и описания PR, комментарии ревью и отчёты проекта по-русски. Перед созданием коммита или переписыванием его сообщения предложи точный заголовок и дождись «да» на этот текст. Для нескольких коммитов покажи все заголовки по порядку, чтобы их можно было подтвердить вместе.
- После блокировки, прерывания или ручного обхода рабочего запуска применяй `ya-zdes-retro` в основном чате, когда есть данные для разбора. Перед явно порученным коммитом примени его к текущей рабочей сессии, сверь журнал и кратко сообщи вывод. Если разбирал эту же сессию раньше, учти события после предыдущего разбора. Улучшения процесса обсуждай отдельно от содержимого коммита.
- Правки самого harness, его отчётов, маршрутизации и проектных инструкций по умолчанию выполняй в текущей сессии с локальными проверками. Для продолжения после прерывания сначала проверь готовый diff и результаты тестов. Отдельные вызовы модели для таких задач запускай по явной просьбе. Прогоны `-DryRun` и тесты с подставным CLI выполняй локально.
- Для остальных задач исследования кода запускай `Inspect` и пересказывай фактический результат. Для новой продуктовой задачи, требующей спецификации, запускай `Plan`. Сам подбирай понятное свободное имя Markdown-файла и связанные пути. Передай пользователю краткий план, критерии приёмки и ссылку на сохранённую спеку.
- Для продуктовой задачи после одобрения плана запускай `Apply` с исходной задачей, затронутыми путями и именем спеки. Если активная спека одна и понятна из переписки, повторно спрашивать имя файла не требуется. Покажи результат кодера, проверки и список замечаний по трём уровням из `reviewFollowUp.summary.chat`, когда он доступен.
- Пока `Apply` работает, передавай в чат смену этапа или причину остановки по строкам `[Apply]` из stderr процесса. Итоговый отчёт читай из stdout.
- В итогах `Apply` учитывай фактический прогон из `checks.afterRepair` или `checks.first`, если исправлений не было. Сообщи, какие автопроверки прошли, какие были недоступны и что известно о причине оставшихся сбоев.
- Если текущую сессию уже запустил harness для отдельного этапа, выполни назначенную роль напрямую. Не вызывай harness рекурсивно. Если запуск завершился ошибкой, сообщи, какой этап заблокирован и сохранилась ли спека.

При запуске через harness модель и глубину рассуждения выбирает маршрутизатор из [SPEC.md](SPEC.md). В обычной сессии Codex применяй правила работы к текущей модели. Для локального поиска начни с `rg` и Git. Обращайся к GitHub через доступный инструмент, когда нужны данные PR, issues или Actions.
